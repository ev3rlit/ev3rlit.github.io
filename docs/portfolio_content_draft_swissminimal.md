## 0. Layout & UX Strategy (읽히는 디자인)
**"화려함보다 가독성(Readability)에 집착합니다."**
채용 담당자는 수많은 포트폴리오를 빠르게 검토해야 합니다. 따라서 시각적 화려함보다는 **'정보가 뇌에 꽂히는 UX'**를 최우선으로 설계했습니다.

### 📐 Format & Print Strategy
- **Web (Desktop)**: **16:9 비율의 슬라이드형 레이아웃**. 각 섹션이 모니터 한 화면(Viewport)에 꽉 차게 들어오도록 설계하여, 마치 프레젠테이션을 보듯 몰입감을 줍니다.
- **PDF (Export)**: 웹에서는 가로형 슬라이드지만, 출력 시에는 **A4 세로(Portrait)** 규격에 맞춰 레이아웃이 자동으로 재배치되도록 `Responsive Print Design`을 적용합니다.

### 🎨 Design Concept: Swiss Style (International Typographic Style)
**"객관적이고 명료한 정보 전달 (Objective & Clarity)"**
스위스 스타일의 철학을 차용하여, 장식적인 요소를 배제하고 콘텐츠의 본질을 '수학적인 질서' 위에서 전달합니다.

- **Grid System (그리드 시스템)**: 철저하게 계산된 그리드 레이아웃을 사용하여 정보에 질서를 부여하고 신뢰감을 줍니다.
- **Minimalist (미니멀리즘)**: "Less is More". 여백을 적극적으로 활용하여 텍스트가 숨 쉴 공간을 만들고, 정보의 과부하를 막습니다.
- **Objective (객관성)**: 감정적인 디자인보다 사실(Fact)과 논리(Logic) 중심의 레이아웃을 지향합니다. 불필요한 색상이나 그래픽을 배제하고, 흑백의 조화와 단 하나의 포인트 컬러로 전문성을 강조합니다.

### 🧠 UX Principles (읽히는 구조)
- **Predictable Pattern (예측 가능성)**: 모든 프로젝트 스토리는 동일한 `7-Step` 구조를 유지하여, 읽는 이가 다음 내용을 예측하고 빠르게 정보를 습득할 수 있게 합니다.
- **Numbered Guides (번호표 유도)**: 시선이 분산되지 않도록 각 섹션과 스텝에 `01`, `02`와 같은 번호를 명시하여, "이 순서대로 읽으면 된다"는 무언의 가이드를 제공합니다.
- **Scan-ability (훑어보기)**: 채용 담당자는 정독하지 않습니다. `키워드`와 `두괄식 요약`만 읽어도 전체 맥락이 파악되도록 합니다.

## 2. Introduction (자기소개)

**"서비스의 안정성을 최우선으로 생각하는 서버 개발자입니다."**

단순히 기능이 동작하는 것을 넘어, 장애가 발생하지 않는 구조를 설계하는 데 집중합니다. 동료들이 "범들갑"이라고 부를 정도로 꼼꼼하게 예외 상황을 대비하며, 이 "호들갑"이 결국 꼼꼼한 Risk Assessment가 되어 시스템의 안정성을 지키는 무기가 됩니다.

> **Why '호들갑'? (The Origin)**
> 첫 프로젝트(BladeX)에서 데이터 정합성 문제로 매일 새벽 수동으로 DB를 수정하며 겪었던 "장애의 공포"가 저를 변화시켰습니다. 그때의 절실함은 "다시는 같은 실수를 반복하지 않겠다"는 원칙이 되었고, 지금의 **'Error as Value'** 철학과 **'선제적 방어 코드'** 작성 습관을 만들었습니다.

- **Values: 무엇을 지키는가**
  - **Data Integrity**: 보여지는 결과(UI)와 실제 처리(DB)는 반드시 일치해야 한다.
  - **Traceability**: 추적 불가능한 에러는 죄악이다.
  - **Efficiency**: 개발자의 1시간은 운영팀의 100시간을 아껴야 한다.

- **Motivation: 무엇이 나를 움직이는가 (직업관)**
  - **"지루함은 혁신의 신호다"**: 반복적인 작업을 단순히 견디기보다, 자동화하거나 새로운 기술로 해결하는 과정에서 즐거움을 느낍니다. 저에게 '금방 질린다'는 것은 '더 나은 방법을 찾을 때가 되었다'는 신호입니다.
  - **"도전은 성장의 연료다"**: 익숙한 기술에 안주하기보다 끊임없이 새로운 시도(AI 도입, 언어 전환)를 즐깁니다. 변화를 두려워하지 않는 성향이 역동적인 게임 개발 환경과 핏이 맞다고 생각합니다.

### 🔑 Appeal Points (3 Keywords)

**Keyword 01 | Risk Assessment (선제적 방어)**
> "동료들이 '범들갑'이라 부르는 꼼꼼함"
> 발생 가능한 모든 엣지 케이스를 사전에 시뮬레이션하고 방어 코드를 작성합니다. 불안함이 곧 시스템의 안정성이 된다고 믿습니다.

**Keyword 02 | Structuring (명쾌한 구조화)**
> "복잡한 로직을 한 장의 지도로"
> 대학 시절부터 키워온 마인드맵 사고방식으로, 복잡한 비즈니스 로직과 아키텍처를 시각화하여 팀원 모두가 이해할 수 있는 '명확한 설계도'로 변환합니다.

**Keyword 03 | Ownership (경계 없는 해결)**
> "내 코드 밖에도 해결책은 있다"
> 클라이언트 이슈, 퍼블리셔 장애 등 내 코드의 범위를 벗어난 문제라도 방관하지 않습니다. 서비스 정상화를 최우선으로, 우회로를 찾고 해결책을 제시합니다.

**01 프로젝트 소개** | **"개발 생산성을 4배 높인 스키마리스 로그 시스템"**

**03 진행한 일** | **배경-문제-해결**

**05 결과물** | **최종 구현 내용**
- 개발자는 구조체 선언만으로 로그 작업 끝. 운영팀은 시각화된 대시보드에서 유저 CS 직접 처리.

**06 성장한 점** | **성과 (Performance)**
- **생산성 향상**: 로그 작업 소요 시간 0.5일 → 1시간 이내로 단축. 개발자는 기능 구현에만 집중할 수 있는 환경 완성.

### 📜 Story 04. 통합 매출 시스템 & 무중단 마이그레이션 (Data Engineering)
**01 프로젝트 소개** | **"사라진 매출 데이터를 되살리고, 다운타임 없이 10만 건을 이관하다"**
- 퍼블리셔 의존으로 인해 누락되었던 핵심 매출 데이터(통화, 환율, 상품정보)를 복원하고, 자체 정산 시스템을 구축했습니다.

**02 프로젝트 개요** | **배경과 목적**
- 퍼블리셔 계약 해지로 자체 서비스를 전환해야 했으나, 기존 DB에는 영수증 원본(Base64)만 있을 뿐 **분석에 필요한 필수 데이터(통화코드, 결제금액, Transaction ID)**가 전무하여 매출 집계가 불가능한 상황이었습니다.

**03 진행한 일** | **배경-문제-해결**
- **문제**: 글로벌 서비스 특성상 환율/통화 정보 없이는 정확한 매출 파악 불가. 운영 서비스 중이라 DB 스키마 변경 부담.
- **해결**: 3대 스토어(Google, Apple, Galaxy) 통합 스키마 설계 및 **백그라운드 마이그레이션 프로세스** 개발.

**04 과정** | **나의 직접적인 액션 + 인사이트**
- **Schema Redesign**: 플랫폼별 고유 테이블(`playstore`, `appstore`...)과 통합 인덱스 테이블(`transaction_index`)로 정규화.
- **Data Recovery**: 기존 `Base64` 영수증을 파싱하고, 부족한 정보는 각 스토어 API를 역으로 조회하여 채워넣는 스크립트 작성.
- **Zero-downtime**: 서버 점검 없이 백그라운드에서 구 데이터를 신규 테이블로 이관하고, 정합성 검증(Transaction ID 전수 조사) 완료 후 스위칭.

**05 결과물** | **최종 구현 내용**
- **10만 건**의 결제 데이터 무결성 확보 및 이관 완료.
- 운영팀이 실시간으로 확인 가능한 **통합 매출 조회 대시보드** 구축 (단일 API로 전 플랫폼 조회).

**06 성장한 점** | **성과 (Performance)**
- **System Stability**: 라이브 서비스 다운타임 **0초**.
- **Lesson**: 편의를 위해 외부(퍼블리셔)에 데이터 분석을 의존했을 때의 리스크를 체감. **"Data Sovereignty(데이터 주권)"**의 중요성 확립.

**07 나의 역량** | **입사 시 기여할 수 있는 부분**
- 레거시 데이터의 두려움을 없앱니다. 복잡하게 얽힌 데이터를 분석하여 살려내고, 서비스 중단 없이 구조를 개선하는 **데이터 엔지니어링 역량**을 갖췄습니다.

- **개선 적용**: BladeX의 아픔을 딛고 **'트랜잭션+롤백'을 초기부터 설계**.
  - 시뮬레이션 제거, 단일 함수 처리로 로직 분기 방지.
  - 에러 발생 시 즉각 롤백으로 데이터 무결성 100% 보장.

**2. Technical Debt: 아쉬움과 반성 (Next Step의 과제)**
- **Client DX (Dev Experience) 부족**: 인메모리 트랜잭션 도구를 도입했으나, 이로 인한 버그가 발생해 클라이언트 개발자가 비즈니스 로직에 온전히 집중하지 못하게 만듦.
- **Observability 부재**: 실시간 모니터링(APM)과 중앙 집계 로그가 없어, 장애 발생 시 `pprof`와 `grep`으로 수동 대응해야 했음. (선제 대응 불가)
- **Infrastructure 한계**:
  - **No RPC Batch**: 네트워크 라운드트립으로 인한 클라이언트 렉 발생.
  - **No Feature Toggles**: 경제 인플레이션 등 사고 발생 시 특정 기능만 끄는 대응 불가능.
  - **Data Integrity**: 엑셀 데이터 간 정합성(Foreign Key) 검증 프로세스 부재로 런타임 에러 빈번.

**3. Strategic Lesson: 퍼블리셔 사태**
- **Data Sovereignty**: 퍼블리셔 해지로 인한 급박한 이관 작업을 겪으며, **"외부 의존성이 있더라도 핵심 유저 데이터는 반드시 자체적으로 관리/백업해야 한다"**는 교훈 체득.

### 📜 Story 06. 실패가 만든 방법론: "주석-먼저 코딩"의 탄생 (Growth)
**01 프로젝트 소개** | **"처절한 실패가 지금의 개발 철학을 만들다"**
- 아이템/인벤토리 코어 로직 개발 중 데이터 정합성 장애를 겪고, 스스로 **Pseudo-code 작성 습관**을 고안했습니다.

**02 프로젝트 개요** | **배경과 목적**
- 게임의 핵심인 경제 시스템(아이템 생성, 소비, 거래)을 구축해야 했습니다. 하지만 서버에는 **트랜잭션/롤백 기능이 없었고**, 에러 핸들링 체계도 부재했습니다.

**03 진행한 일** | **배경-문제-해결**
- **문제**: 트랜잭션이 없는 인메모리 구조에서, 클라이언트에게 보여주는 **'시뮬레이션 결과'**와 실제 DB에 **'처리되는 결과'**가 달라지는 치명적인 데이터 불일치 이슈 발생.
- **증상**: 확률적 보상 아이템에서 시뮬레이션 결과 ≠ 실제 처리 결과 (확률이 다시 돌아감).
- **고통**: 매일 새벽 깨진 데이터를 수동으로 DB에 접속해 수정해야 했고, 유저들의 신뢰를 잃는 아픔을 겪었습니다.

**04 과정** | **나의 직접적인 액션 + 인사이트**
- 당시에는 근본적인 해결(트랜잭션 도입)을 하지 못했습니다. 하지만 **버그를 줄이기 위한 나만의 방법**을 고민한 결과:
  - **"주석-먼저 코딩 (Pseudo-code First)"** 습관을 스스로 고안
  - API 구현 전, 필요한 **실행 순서를 자연어로 주석 작성** → 주석에 맞춰 코드 구현
  - 이 방식이 가장 버그가 적고 효율적임을 체감, **지금까지도 유지 중인 개발 철학**이 됨

**05 결과물** | **최종 구현 내용**
- (시스템적 해결은 못했으나) 개인 방법론 확립: **Think First, Code Later**

**06 성장한 점** | **배운점 (Turning Point)**
- **"Atomicity(원자성)는 타협할 수 없는 가치"** 체득
- 이 실패는 훗날 삼국블레이드에서 **'Error as Value'**와 **'트랜잭션 미들웨어'**를 1순위로 설계하게 만든 결정적 계기
- "가장 큰 배움은 성공이 아닌 처절한 실패에서 온다"

**07 나의 역량** | **입사 시 기여할 수 있는 부분**
- 실패를 숨기지 않고 **방법론으로 승화**시킵니다. 과거의 실수를 반복하지 않는 견고한 설계와, 코딩 전 충분히 생각하는 습관을 갖춘 개발자입니다.
